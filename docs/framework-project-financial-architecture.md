# Фреймворк: проектирование финансовой архитектуры проекта

Чек-лист вопросов, которые нужно закрыть для любого нового проекта (клиента)
на платформе, прежде чем начинать реализацию. Родился при разборе Cloudsix
(2026-09-03) — см. [[2026-09-03 архитектура финансов Cloudsix]] в вики.

Цель — не переизобретать структуру заново для каждого клиента: у каждого
проекта своя финансовая специфика, но вопросы, которые нужно задать, одни
и те же.

## 1. Источники дохода/данных

Какие площадки и каналы приносят деньги или данные:
- Маркетплейсы (WB, Ozon, ...) — обычно основной источник, есть отчёты
- Банк/расчётный счёт — нужен, если аналитика должна включать реальное
  движение денег (кэшфлоу), а не только цифры площадки
- Прочие каналы (свой сайт, опт и т.д.)

Для каждого источника: в каком формате приходят данные (API, .xlsx-отчёт,
банковская выписка), с какой периодичностью, кто их выгружает.

## 2. Юридическая/бизнес-структура

- Сколько юрлиц у клиента
- Сколько кабинетов на каждой площадке, к какому юрлицу/бренду относится
  каждый
- Нужна ли консолидация «по компании в целом» отдельно от разреза по
  бренду/юрлицу

Модель данных платформы уже поддерживает это без изменений:
`projects` (1) → `project_cabinets` (N, с полем `platform`) для привязки
кабинета к проекту, и `brands` (M) ↔ `brand_cabinets` (N) для
бизнес-группировки кабинетов внутри проекта — см.
`src/schema_projects.sql`. Один кабинет = один проект (1:N), бренд и
кабинет — многие-ко-многим.

**Ловушка нейминга кабинетов (нашлась на Cloudsix, 2026-09-03):** если один
и тот же бренд представлен на нескольких площадках (WB и Ozon под разными
юрлицами — обычная практика), кабинет на каждой площадке — это ФИЗИЧЕСКИ
разный аккаунт (по определению глоссария), но `project_cabinets`
дедуплицируется по `ORDER BY (cabinet)` — без площадки в ключе. Если оба
кабинета назвать одинаковой строкой (например, именем бренда), они
схлопнутся в один. Проверять до первой загрузки второй площадки для уже
существующего бренда: включать площадку в строку `cabinet`, если бренд
уже есть на другой площадке под другим именем (например `"Бренд WB"` /
`"Бренд Ozon"`), не переименовывая задним числом кабинеты, под которыми
уже загружены исторические данные.

## 3. Требуемые финансовые результаты

Что клиент/команда должны увидеть на выходе — не любой пункт актуален
для каждого проекта:
- **P&L** — выручка минус все расходы (комиссии площадки, логистика,
  реклама, налоги и т.д.) по периодам
- **Юнит-экономика** — маржинальность на уровне SKU/товара
- **Кэшфлоу** — когда деньги реально приходят на счёт (площадки платят
  с задержкой/авансами — это не то же самое, что выручка по отчёту)
- **Сверка/контроль** — расхождения внутри одного источника (сводный vs
  детальный отчёт) и между источниками (отчёт площадки vs банк)

**Спросить сразу, до начала работы:** ведёт ли клиент кэшфлоу/ДДС уже в
стороннем сервисе (найдено на Cloudsix, 2026-09-03— готовый каталог
банковских счетов по всем юрлицам в ПланФакте, planfact.io). Если да —
может быть дешевле интегрироваться/выгружать оттуда, чем строить загрузку
банковской выписки с нуля.

## 4. Специфичные для бизнеса статьи

У каждого продавца на маркетплейсах могут быть операции вне стандартных
отчётов площадки, которые тем не менее должны попасть в P&L/кэшфлоу.
Примеры, встреченные на практике (уточнять терминологию и механику у
клиента для каждого случая — фиксировать в глоссарии):
- **Самовыкупы** — покупки товара с других аккаунтов для накрутки
  рейтинга/продаж; обычно не отражены в отчётах площадки как отдельная
  статья, данные приходится собирать отдельно
- **Карго** — расчёты с перевозчиком за доставку товара (например, из
  Китая на склады маркетплейса); отдельный контрагент, отдельные
  акты/выписки
- **Расчёты с поставщиком/закупочным агентом** — оплата закупки товара
  (предоплата, партиями), отдельный источник данных

Для каждой такой статьи нужно решить: это (а) отдельный источник данных
со своим модулем ingest (по аналогии с WB/Ozon), или (б) категория
расходов, которая просто вручную заносится в кэшфлоу/P&L без
автоматической загрузки. Критерий — регулярность и объём: если данные
приходят системно и часто (каждую неделю, десятки строк) — заводить
модуль; если разово/вручную — категория без автоматизации.

## 5. Схема данных

Правило платформы (см. `docs/vision.md`): каждый источник — независимый
модуль (скачал/принял → разобрал → загрузил в ClickHouse), у каждого
клиента — общая база ClickHouse, но проект/бренд/кабинет как разрез
внутри неё (см. `schema_projects.sql`), не отдельная физическая БД на
клиента (это разошлось с более ранней формулировкой в `vision.md` —
уточнить/синхронизировать при следующей правке видения).

Проверки расхождений — конфигурируемые правила (YAML), не хардкод.

## 6. Витрины (Metabase)

По каждому требуемому финансовому результату (п.3) — минимум одна Model
как источник истины для формул + карточки/дашборд поверх неё. Соглашения
по именованию и структуре — `.claude/knowledge/architecture-standarts.md`.

## Как использовать этот чек-лист

1. Пройтись по пп. 1–4 с клиентом/владельцем проекта, зафиксировать ответы
   в отдельной заметке `knowledge/business/<дата> архитектура финансов
   <проект>.md` в вики проекта
2. Сверить с существующей моделью данных (п.5) — обычно новых таблиц не
   требуется, только заполнение существующих (`projects`, `brands`, ...)
   и, при необходимости, новый ingest-модуль по образцу `wb_core.py`
3. Спроектировать витрины (п.6) под конкретные пункты из п.3
4. Если по ходу разбора нашёлся термин, которого нет в глоссарии —
   добавить в `docs/glossary.md`
