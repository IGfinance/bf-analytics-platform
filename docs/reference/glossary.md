# Тезаурус проекта

> **Коротко:** словарь терминов платформы — что значит «Проект», «Кабинет», «Бренд», «Сверка» и другие слова, которые здесь используются в специфичном смысле.
> **Когда открывать:** встретил в другом документе или в коде слово, в значении которого не уверен.
> **Связанные документы:** [architecture-map.md](../product/architecture-map.md) — где эти сущности живут технически.

Термины, которые в проекте называют по-разному, но должны пониматься
однозначно. Пополняется по ходу `/write-task` — если в разговоре
встречается неоднозначный термин или синоним уже описанного, здесь
фиксируется единственно верное название и его точное значение.

Формат таблицы:

| Термин | Определение | Синонимы (больше не использовать) | Где живёт |
|---|---|---|---|

## Общие термины (все проекты)

Платформа с 2026-09-12 мультипроектная (сейчас — CloudSix и Реальт), эти
термины не привязаны к одному источнику или клиенту.

| Термин | Определение | Синонимы (больше не использовать) | Где живёт |
|---|---|---|---|
| **Проект** | Клиент платформы (сейчас CloudSix, Реальт). Верхний уровень, к которому привязаны пользователи, кабинеты и бренды; у каждого проекта — своя физическая БД в ClickHouse (имя БД = `projects.slug`) | клиент | таблица `projects` (БД `control`) |
| **Кабинет** | Учётная запись продавца на площадке (WB, Ozon) или иная организационная единица внутри проекта. Один проект может держать несколько кабинетов | аккаунт, магазин | таблица `project_cabinets` (в БД каждого проекта), колонка `cabinet` в таблицах-источниках |
| **Бренд** | Бизнес-группировка кабинетов внутри проекта: обычно 1 бренд = 1 кабинет, но бывает 2 бренда в одном кабинете или 1 бренд размазан по 2 кабинетам — связь многие-ко-многим. **Не путать** с колонкой `brand` в `wb_reports` — это атрибут товара (бренд SKU) из самого отчёта WB, построчный и не связанный с этой сущностью | — | таблицы `brands`, `brand_cabinets` (в БД каждого проекта) |
| **Сверка** | Автоматическое сопоставление цифр между двумя независимыми источниками одной площадки (детальный vs сводный отчёт WB, либо API vs `.xlsx` для WB/Ozon) — по общей сумме и по каждой метрике модели отдельно | reconciliation | таблицы `wb_reconciliation_results`, `api_reconciliation_results` |
| **ingest** | Загрузка сырого файла или ответа API в ClickHouse: разбор/запрос → маппинг колонок → запись строк | — | `ingest_*.py`, `*_core.py` в `src/` |
| **Модель** (Metabase Model) | Зафиксированный SQL-запрос с формулами метрик. Единственное место, где формула написана словами SQL — остальные карточки на неё ссылаются, а не копируют код | — | Metabase, `src/metabase_queries/*.sql` |
| **Метрика** (Metabase Metric) | Готовая агрегация поверх Модели (например, сумма по колонке «Продажи»), переиспользуемая как блок в других карточках | — | Metabase |

## Отчёты WB

| Термин | Определение | Синонимы (больше не использовать) | Где живёт |
|---|---|---|---|
| **Еженедельный отчёт** | Подробный построчный отчёт со всеми операциями за неделю (продажи, возвраты, логистика, штрафы и т.д. — каждая операция отдельной строкой) | сырые данные, детальный отчёт, сырой отчёт | таблица `wb_reports` |
| **Сводный отчёт** | Отчёт с итоговыми суммами по показателям (продажи, штрафы, логистика и т.д.) за период — агрегат нескольких еженедельных отчётов | сводка, summary-отчёт | таблица `wb_report_summary` |
| **№ отчёта (report_number)** | Идентификатор конкретного отчёта, присваивается WB, парсится из имени файла | номер отчёта | колонка `report_number` в `wb_reports` / `wb_report_summary` |

## Реальт (клиника)

Первый проект за пределами маркетплейсов (WB/Ozon) — источники и метрики
заведены ТЗ 02, развиваются с 2026-09-17 напрямую (см. `docs/product/vision.md`).

| Термин | Определение | Синонимы (больше не использовать) | Где живёт |
|---|---|---|---|
| **Клиентикс** | CRM клиники, откуда выгружаются визиты и приёмы (CSV-выгрузка или CLI-загрузка пачкой) | — | `klientiks_core.py`, таблица `klientiks_operations` |
| **Визит** | Одна строка Клиентикс — приём пациента у конкретного сотрудника в конкретный день; единица, от которой считаются метрики «Средний чек», «Новые клиенты» и когортные визиты | приём | `klientiks_operations`, VIEW `realt_visits_categorized` |
| **Начисления** | Один из финансовых источников Реальта из Google-Таблицы (наряду с «Расчетным счётом» и «Наличными») — тянется напрямую через Google Sheets API, без выгрузки файла | — | `realt_gsheets_core.py` → `ingest_accruals`, таблица (см. `schema_realt_gsheets.sql`) |
| **ФОТ** (Фонд оплаты труда) | Все выплаты сотрудникам клиники за период — оклады, бонусы, проценты с приёмов — по ролям (Психиатры/Психологи/Администраторы/Управление/Маркетинг/Шмилович). Источник — выгрузка из Google-Таблицы | зарплатный фонд, payroll | таблица `realt_payroll` |
| **department / role_group** | Два независимых способа категоризировать сотрудника в `realt_payroll`/`realt_employees`: `department` — оргструктурный отдел (значение может меняться во времени у одного сотрудника), `role_group` — категория для формул метрик (например, «ФОТ ШАА»). С 2026-09-19 `role_group='ФОТ ШАА'` вычисляется из `department='ШАА'` **с учётом периода** (join по `employee_id` + месяц), а не «сотрудник когда-либо был в этом отделе» — иначе смена отдела задним числом искажает историю | — | `realt_payroll`, `realt_employees`, VIEW `realt_payroll_categorized` |
| **ШАА** | Подразделение клиники, которое по договорённости с владельцем 2026-09-19 исключается/выделяется отдельно в ряде выручка-/ФОТ-метрик (например, «Выручка без ШАА», «Выручка с первых визитов»). Не путать: до 2026-09-17 то же самое исключение шло по имени сотрудника (Шмилович), а не по отделу — цифры при этом менялись, см. `docs/product/vision.md` | — | `department='ШАА'` в `realt_payroll`/`realt_employees` |

## Как пополнять

Во время `/write-task`, если появляется термин, который может быть понят
по-разному (в том числе если пользователь и Илья используют для одного и
того же разные слова) — сформулируй определение, уточни у пользователя, если
неочевидно, и добавь строку в таблицу выше (или заведи новый раздел, если
термин не про отчёты WB).
