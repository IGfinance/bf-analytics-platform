# Куда мы движемся — видение платформы аналитики

Этот файл — ориентир для того, как отдельные ТЗ складываются в общую картину.
Перед тем как браться за новое ТЗ из `tz/`, полезно свериться, какую часть
этой картины оно закрывает.

## Что строим

Внутренний инструмент команды Finance Black (не отдельный продукт для
клиентов) — по каждому клиенту:
1. **Автоматически собирает** данные из разных источников (WB, Ozon, банк и
   т.д.) вместо ручного сведения в Excel.
2. **Проверяет** их между собой на расхождения — как внутри одного источника
   (сходятся ли отчёты одной площадки), так и между источниками (сходится ли
   отчёт площадки с банковской выпиской).
3. **Показывает** результат в дашбордах Metabase — и по каждому клиенту
   отдельно, и (для клиентов с несколькими кабинетами/брендами) сводно.

## Как это устроено технически (коротко)

- Каждый источник данных (WB, Ozon, банк, ...) — свой независимый модуль
  с одинаковым принципом: скачал/принял файл → разобрал → загрузил в
  ClickHouse. Новый источник = новый модуль по этому же принципу, не
  переделка существующих.
- У каждого клиента — своя база данных в ClickHouse (не общая таблица на
  всех) — чтобы данные разных клиентов физически не пересекались.
- Проверки расхождений — это конфигурируемые правила (как сейчас
  `reconciliation_rules_wb.yaml`), а не захардкоженная логика в коде —
  правил будет постепенно много, они копятся по мере того, как находятся
  новые способы что-то проверить.

## Бэклог (мелкие доработки, не тянут на отдельное ТЗ)

- **Канарейка на переименование статей Ozon.** `ozon_metrics_by_cabinet_month`
  (см. `src/schema_ozon_metrics_views.sql`) считает "Выручка к перечислению"
  через захардкоженный список названий `service_group`/`accrual_type` (по
  образцу того, как WB-модель уже обрабатывает переименование "Продвижение
  ВБ"→"Продвижение WB"). 2026-09-08 поймали живое переименование Ozon
  ("Услуги агентов"→"Услуги партнёров") только руками, сравнив с
  `sum(total_amount)`. Нужна проверка в `check_ozon.py` (по образцу уже
  существующих там проверок), которая раз в прогон сверяет
  `payable_total` из VIEW с `sum(total_amount)` по всем строкам за тот же
  месяц — расхождение = сигнал, что Ozon добавил/переименовал ещё одну
  группу услуг, которую формула не учитывает.

- **Диск на VPS почти заполнен.** На 2026-09-12 занято 18 из 20GB (97%,
  ~600MB свободно) на `91.245.225.207` — не из-за миграции БД (сам
  ClickHouse весит ~100MB). Разобраться, что именно ест место (старые
  бэкапы? логи? venv нескольких деплоев?), и завести алерт на заполнение
  диска — иначе следующий деплой/миграция/бэкап рискует не влезть и
  уронить прод.

- **Узкие ClickHouse-пользователи для Metabase.** Сейчас Metabase
  подключается к `cloudsix` под тем же широким пользователем `default`,
  что и сам webapp/CLI-скрипты (временно, после переноса CloudSix в
  `cloudsix` 2026-09-12) — GRANT-изоляция между проектами для аналитика
  ещё не настоящая, только БД разделены физически. Нужно завести
  `metabase_cloudsix`/`metabase_realt` с SELECT только на свою БД и
  переключить на них Metabase-подключения (см.
  `.claude/plans/iridescent-brewing-scroll.md` → «Кто куда подключается»).
  Плюс `scripts/provision_project.py` — пока Реальт заведён вручную,
  третьего клиента лучше заводить воспроизводимым скриптом.
