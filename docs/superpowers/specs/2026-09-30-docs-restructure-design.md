# Реорганизация живой документации bf-analytics-platform

Дата: 2026-09-30
Ветка: `Docs`
Статус: утверждено пользователем, готово к реализации

## Зачем

Сейчас документация читаема, но плохо организована: `DESIGN.md`/`WIKI.md`
лежат в корне репозитория рядом с README, а внутри `docs/` девять файлов
разных жанров (видение платформы, технический снимок архитектуры,
чек-лист для нового клиента, глоссарий, разведка нового источника,
LaTeX-формулы) свалены в одну кучу без деления по темам. Нет единого входа
(индекса), который объяснял бы, что где искать. Часть документов написана
плотным техническим языком без пояснения терминов для человека без
контекста.

## Цель

1. Разложить документы по тематическим папкам — по названию папки сразу
   понятно, что внутри.
2. Переписать текст каждого документа так, чтобы его понял человек без
   контекста проекта (термины вроде ClickHouse/VIEW/сверка поясняются при
   первом употреблении), не теряя ни одной технической детали — цифры, SQL,
   схемы, формулы, правила остаются точными.
3. Завести единый входной индекс `docs/README.md`.
4. Попутно поправить фактические неточности, найденные при анализе
   (см. раздел «Точечные фактические правки»).
5. Обновить взаимные ссылки между документами после переезда файлов.

## Не входит в объём (осознанно)

- `work/tz/active|done|review/*` — исторический архив ТЗ и код-ревью,
  переписывать задним числом бессмысленно, не трогаем.
- Любой код (`src/`, `webapp/`, `scripts/`, `tests/`) — не меняем.
- `LICENSE`, `package.json`, `.env.example`, `requirements.txt` — не трогаем.
- Пересборка `docs/reference/formulas/realt.pdf` — на рабочей машине нет
  xelatex/tectonic; фиксируем этот факт в документе, саму пересборку не
  делаем.
- `.claude/knowledge/architecture-standarts.md` — вне `docs/`, отдельный слой
  для агента, не для человека; не переносим и не переписываем.

## Единый шаблон документа

В начале каждого переносимого файла (кроме formulas/realt.tex — это LaTeX,
шаблон к нему не применяется) — блок из трёх частей:

```markdown
> **Коротко:** 1–2 предложения, что это и для кого.
> **Когда открывать:** конкретные ситуации использования.
> **Связанные документы:** ссылки на 2–4 смежных файла.
```

Дальше — сам текст. Правила переписывания:

- термин поясняется при первом употреблении в файле (не выносить в отдельный
  глоссарий-подстрочник — вставка прямо по тексту, коротко, в скобках или
  отдельным предложением);
- все таблицы, SQL-фрагменты, mermaid-диаграммы, числа, имена таблиц/колонок
  — переносятся один в один, без изменения смысла;
- если абзац уже понятен и хорошо структурирован (это касается прежде всего
  `architecture-map.md` — он уже написан достаточно ясно, с таблицами и
  диаграммами) — не переписывать ради переписывания, только добавить шапку
  и поправить найденные фактические неточности;
- заголовки разделов — по смыслу, не более 2 уровней вложенности внутри
  файла, чтобы не терять ориентацию.

## Точечные фактические правки (не только стиль)

- **`docs/product/architecture-map.md`**: строка снимка вверху утверждает
  дату **2026-09-23**, но по факту тело документа уже содержит правки от
  **2026-09-27** (пересборка `wb_api_realization` под новое финансовое API,
  метрика `sales_corrections`/сведение «К перечислению» с недельной сводкой).
  То есть контент правился инкрементально прямо в файле, а шапка-дата не
  обновлялась. Правка: заменить фиксированную дату на формулировку без
  риска повторного протухания, например «Обновляется по ходу изменений
  архитектуры, последняя правка контента — 2026-09-27» — и свериться на
  момент правки с `git log -1 --format=%cd -- docs/architecture-map.md`,
  чтобы дата была точной на момент коммита.
- **`README.md`**: сейчас в разделе «Структура» и «Документация» есть прямые
  пути `DESIGN.md`, `WIKI.md`, `docs/glossary.md`, `docs/vision.md` — все
  четыре переезжают, ссылки и блок дерева каталогов должны быть обновлены
  на новые пути.
- **Общий проход grep по всем переносимым файлам** на предмет относительных
  ссылок друг на друга (`docs/vision.md`, `DESIGN.md`, `docs/glossary.md` и
  т.д. могут упоминаться внутри текста, не только в README) — поправить
  после `git mv`.
- **`docs/reference/formulas/README.md`**: явно зафиксировать, что
  `realt.pdf` не пересобирался после правок `realt.tex` от 2026-09-24 (на
  машине нет xelatex/tectonic) — факт уже есть в `docs/vision.md`, но в
  самом `formulas/README.md` его нет.

## Порядок работ (для implementation-плана)

1. `git mv` — создать новые папки, перенести 4 файла из корня/docs в
   тематические подпапки под новыми именами.
2. Грep-проверка и правка перекрёстных ссылок (README.md и содержимое
   каждого перенесённого файла).
3. Переписать каждый файл по шаблону (шапка + пояснение терминов), внести
   точечные фактические правки из раздела выше.
4. Написать новый `docs/README.md` — индекс с одной строкой на каждый файл
   и подпапку.
5. Проверка: `grep -rn "DESIGN.md\|WIKI.md\|docs/vision.md\|docs/glossary.md\|docs/architecture-map.md\|docs/framework-project-financial-architecture.md\|docs/odata-alabuga-bottling-entities.md" --include="*.md" .` — должно вернуть только ожидаемые совпадения (внутри `work/tz/*`, которые мы осознанно не трогаем).
6. Коммит в ветку `Docs` (не в `master`).

## Риски

- Ссылки на старые пути документации могут быть также в `work/tz/*`
  (исторические ТЗ) — их **не правим** (это исторический снимок на момент
  написания ТЗ, менять факт истории некорректно), но стоит явно упомянуть
  в PR-описании, что такие ссылки в архиве ТЗ остаются битыми намеренно.
- `architecture-map.md` большой (341 строка) и технически плотный — риск
  случайно исказить факт при «причёсывании» текста. Митигация: менять только
  формулировки и шапку, не трогать таблицы/диаграммы/цифры без явной сверки
  с источником.
