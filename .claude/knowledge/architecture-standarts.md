# Архитектурные стандарты — bf-analytics-platform

Живой документ. Пополняется по ходу задач: автоматически через `/review-task`
(когда находится новый повторяющийся тип проблемы) и вручную.

Обязателен к прочтению перед написанием кода в этом репозитории, в том числе
AI-инструментами подрядчиков (Claude Code, Cursor).

## Жёсткие правила (нельзя нарушать)

- Никаких секретов в коде — только через `.env` (см. `.env.example`,
  `webapp/.env.example`)
- Конфигурируемость: то, что может измениться (URL, лимиты, ключи, пути,
  идентификаторы) — выносится в конфиг/переменные окружения, не хардкодится
  в теле функции
- Модульность: одна функция/скрипт — одна ответственность. Не смешивать
  получение данных, обработку и вывод в одном блоке без возможности
  переиспользовать части по отдельности
- Любой внешний вызов (API, БД, файловая система, сеть) обязан обрабатывать
  ошибки — без try/except или эквивалента код не принимается
- Логирование по глобальным правилам (`~/.claude/CLAUDE.md → Логирование`):
  уровни DEBUG/INFO/WARNING/ERROR/CRITICAL, без секретов и PII
- Новый функционал или починка бага → тест или явный ручной чек-лист проверки

## Соглашения по Metabase

Применяется к любым сущностям, создаваемым в Metabase (dashboards.finance-black.ru).

- **Именование:** `"Сущность - Название"`, где «Сущность» — один из шести
  типов:
  - **База данных** — прямое подключение к ClickHouse в Metabase (Admin →
    Databases). Не карточка, но верхний уровень иерархии: всё остальное
    строится поверх неё
  - **Модель** — Metabase Model (`type: "model"`): зафиксированный SQL-запрос,
    на который ссылаются остальные карточки через конструктор вместо
    копирования SQL. Формулы метрик живут здесь один раз, а не в каждой
    карточке отдельно — см. «Один источник истины для формул» ниже
  - **Метрика** — Metabase Metric (`type: "metric"`): сохранённая агрегация
    поверх модели/таблицы (например, `sum("Продажи")`), переиспользуемая как
    готовый блок в конструкторе запросов
  - **Таблица** — SQL-запрос с выгрузкой в табличном виде (Metabase question
    с табличным результатом). Служебная сущность — готовит данные (обычно
    развёрнутые построчно/unpivot) для Визуала, сама на дашборды не выносится
  - **Визуал** — визуализация таблицы: сводная (pivot), график и т.д.
    (Metabase question с типом визуализации, отличным от Table). Единственный
    тип карточки, который кладётся на дашборд вместе с фильтрами
  - **Дашборд** — комбинация визуалов и фильтров на одном экране

  Примеры: `Таблица - Метрики для отчета Wb`,
  `Модель - WB метрики по кабинету и месяцу`.

- **Метрика и Визуал — дополнительно указывают клиента.** Начиная с
  2026-09-15 платформа мультиклиентная (CloudSix, Реальт — модели 98-100 в
  коллекции 8), поэтому для Метрик и Визуалов имени одной «Сущность -
  Название» уже недостаточно: `"Метрика - Клиент - Метрика Площадка"` /
  `"Визуал - Клиент - Название Площадка"`, где «Площадка» — маркетплейс
  (WB/Ozon), только если применимо, всегда последним словом. Если в
  исходном названии метрики площадка уже была зашита текстом (например,
  «Комиссия ВБ», «Продвижение WB») — при переименовании эта часть
  вычищается, чтобы не задваивалась с добавленным суффиксом площадки.
  Примеры: `Метрика - CloudSix - Выручка Ozon`, `Метрика - CloudSix -
  Комиссия WB` (было «Комиссия ВБ»), `Визуал - CloudSix - Полный отчет по
  артикулу WB`.

  Та же схема — и для Таблиц-сверок в папке `Тесты / Чеки`: они по своей
  природе клиент- и площадка-специфичны (сравнивают конкретный отчёт
  конкретного клиента), поэтому тоже получают Клиента и Площадку в имени.
  Примеры: `Таблица - CloudSix - Сверка API vs xlsx по метрикам Ozon`,
  `Таблица - CloudSix - Сверка сводный отчёт vs сырые данные по метрикам WB`.
  Служебные Таблицы-основания для Визуалов (например,
  `Таблица - Полный отчет Wb (в строки)`) клиента в имени НЕ
  указывают — это внутренняя техническая карточка, не читается человеком
  напрямую. Модель/Дашборд клиента в имени тоже не указывают.

- **Описания (`description`) — единый регистр на человеческом языке, без
  исключений по типу карточки (решение 2026-09-21).** До этого поле
  `description` использовалось вперемешку под разные задачи — бизнес-
  объяснение для клиента, служебные заметки разработки («Источник —
  карточка 179 (long-формат)», «не синхронизировано с продом»), changelog
  задним числом — и превращалось в помойку. Клиент видит только папку с
  Дашбордами (Модели/Таблицы/Метрики — служебные, в коллекции отдельно),
  но это не повод писать их `description` техническим языком: правило
  одно на все пять типов сущностей. **Запрещено в `description`:**
  SQL/ClickHouse-идентификаторы, ID карточек, даты ревью/синхронизации,
  ссылки на файлы репозитория, changelog — это остаётся в SQL-шапке
  карточки (`src/metabase_queries/*.sql`) и `docs/architecture-map.md`,
  дублировать не нужно. 1–3 предложения, без воды. Единственное
  исключение — Метрика может заменить прозу компактной математической
  записью формулы (например, «Средний чек = Выручка / Визиты»).

  Обязательное содержание по типу:

  | Тип | Что обязательно в `description` |
  |---|---|
  | Дашборд | Бизнес-смысл одной фразой + нетривиальная механика чтения (переключатели, с чем что сравнивается) + охват периода, если не очевиден из фильтров |
  | Визуал | Что изображено (метрика × разрез: строки/столбцы/легенда) + единица измерения, если не очевидна; для ratio-исключения (см. ниже) — явно, что «За год» не сумма месяцев |
  | Модель | Агрегат человеческими словами (не «SELECT из VIEW») + грейн строки (месяц? врач?) + бизнес-допущения, меняющие смысл цифры |
  | Таблица | Для какого Визуала готовит данные + формат человеческими словами («одна строка = метрика за месяц», не «long-формат») |
  | Метрика | Формула человеческим языком + компактная математическая запись + единица измерения |

  Пример (Реальт, до → после). Визуал `id 180`: было «Pivot-таблица
  расходов... Источник — карточка 179 (long-формат)» → стало «Расходы
  клиники по группам (Помещение/Маркетинг/Административные) по месяцам».
  Дашборд `id 5`: было «Копия realt-bi /clinic → Юнит-экономика, посчитана
  по логике на ClickHouse/Metabase» → стало «Юнит-экономика клиники по
  месяцам: выручка, визиты, клиенты, ФОТ и прибыль после ФОТ».

- **Правило дашбордов: только Визуалы и фильтры — с одним осознанным
  исключением (см. ниже).** На дашборд выносятся преимущественно
  карточки-Визуалы (display, отличный от Table) и фильтры (dashboard
  parameters). Карточки-Таблицы — служебные, готовят данные для Визуала
  (unpivot и т.п.) и остаются в коллекции, на дашборд не добавляются. Если
  на дашборде обнаружена Таблица — это повод пересобрать её в Визуал
  (пример: 2026-09-15, `Дашборд - WB Полный отчёт по артикулу` —
  `Таблица - Полный отчет Wb по артикулу` заменена на
  `Визуал - Полный отчет Wb по артикулу` + добавлен
  `Визуал - Полный отчет Wb по артикулам (сравнение)`, см. золотой пример
  ниже).

  **Исключение: сводные Таблицы с ratio-метриками (найдено 2026-09-19,
  дашборды Реальта 5/6/7/8).** MBQL-пивот (`display: pivot`) считает
  столбец «Итого»/«За год» ТОЙ ЖЕ агрегацией (`sum`), что и обычные ячейки
  — у него физически нет способа применить другую формулу для итога
  конкретной строки-метрики. Это ломается для любой строки, где годовое
  значение — не сумма месячных (средний чек, доля %, X на клиента и
  т.п.): `sum(avg_check по 12 месяцам)` — бессмысленное число, верное
  значение — `sum(выручка за год) / sum(визиты за год)`. Чтобы получить
  такую строку через MBQL-пивот, нужен ШИРОКИЙ формат данных (revenue и
  visits как отдельные колонки), а чтобы название метрики стало строкой
  через `breakout`, данные обязаны быть в ДЛИННОМ формате (одна колонка
  `value` на все метрики) — эти два требования несовместимы в одном
  MBQL-запросе. Поэтому: **разрешается** карточка-Таблица (native SQL,
  вручную строящая и разворот, и ratio-формулу для «За год») напрямую на
  дашборде, ЕСЛИ хотя бы одна строка в ней — не аддитивная метрика.
  Обязательные условия исключения (иначе это обычное нарушение правила
  выше, не исключение):
  1. Каждая ratio-строка помечена как такая в SQL-комментарии карточки
     (`realt_monthly_metrics.sql` — пример) — с явной формулой «За год».
  2. Та же формула описана в клиентском LaTeX-документе формул
     (`docs/formulas/<клиент>.tex`) — отдельным подразделом, не только в
     общей формуле метрики.
  3. `COMMENT COLUMN` соответствующей колонки VIEW явно предупреждает, что
     колонка — ratio и её нельзя суммировать по месяцам для годового
     итога (см. `avg_check`/`new_client_visits_3m_avg` в
     `schema_realt_metrics_views.sql`) — иначе бот, читающий только
     `system.columns`, молча просуммирует и получит неверное число (см.
     «Семантический слой для AI-бота» ниже).
  4. Отмечено в `docs/architecture-map.md` (раздел про Metabase) — какая
     именно карточка и почему является исключением.

- **Фильтр можно привязать к одному Визуалу или ко всем.** Dashboard
  parameter маппится (`parameter_mappings`) на dashcard индивидуально — можно
  оставить только на одной карточке (управляет только ей) или продублировать
  маппинг на все Визуалы дашборда (тогда один виджет фильтра управляет всеми
  сразу). На `Дашборд - WB Полный отчёт по артикулу` изначально сделали
  первый вариант (Кабинет/Артикул только на `Визуал - Полный отчет Wb по
  артикулу`, Период только на «сравнение»), но по итогу пользователь попросил
  все три фильтра применимыми к обоим Визуалам сразу — так удобнее для
  анализа. Итоговое состояние: Кабинет, Артикул и Период замаплены на оба
  dashcard'а. Единственное условие технически — у карточки-Таблицы под
  Визуалом должно быть само поле, на которое таргетится фильтр (например,
  для фильтра Кабинет на «сравнении по артикулам» пришлось добавить колонку
  `cabinet` в лежащую под ним Таблицу — изначально её там не было, так как
  разрез не предполагал фильтр по кабинету).

- **Фильтр со списком значений (чекбоксы) вместо ручного ввода.** Dashboard
  parameter с `values_query_type: "list"` рендерится как список с чекбоксами
  (множественный выбор) вместо текстового поля. Два способа получить список
  значений:
  - **По умолчанию** («from connected fields», `values_source_type` не
    задан) — Metabase сам берёт distinct-значения РЕАЛЬНОГО поля БД (не
    виртуальной колонки карточки), на которое таргетится фильтр. Требует,
    чтобы `dashcard.parameter_mappings[].target` указывал на настоящий
    `field_id` из Metabase (`["dimension", ["field", <field_id>, {...}]]`),
    а не на поле по имени из карточки-обёртки. Только этот способ **даёт
    каскадные (зависимые) фильтры** — см. ниже.
  - **Из карточки** (`values_source_type: "card"` +
    `values_source_config: {card_id, value_field}`) — Metabase выполняет
    `SELECT DISTINCT <value_field> FROM <card>`. Годится, когда нужного
    поля нет как настоящего `field_id` (например, значение — вычисляемое
    выражение), но **несовместим с каскадными фильтрами** (см. ниже) —
    кастомный источник отключает зависимость.

- **Каскадные (зависимые) фильтры.** У дочернего параметра — поле
  `filteringParameters: ["<id родительского параметра>"]`. Тогда список
  значений дочернего фильтра сужается под уже выбранное значение
  родительского (Metabase сам строит `SELECT DISTINCT child FROM table WHERE
  parent = <выбрано>` через chain-filter). Жёсткие условия: (1) оба поля —
  реальные `field_id` одной физической таблицы (или связаны FK на уровне
  метаданных БД — JOIN внутри Model/question не считается), (2) значения
  обоих фильтров — «from connected fields», не `static-list`/`card`. На
  `Дашборд - WB Полный отчёт по артикулу`: Кабинет/Артикул сначала сделали
  через `values_source_type: "card"` (первая попытка списка — простая, но
  без каскада), затем пересобрали на реальные `field_id` таблицы
  `wb_metrics_by_sku_month` (`cabinet` — 1044, `sku` — 1046) и добавили
  `filteringParameters` на Артикул → Кабинет ограничивает список артикулов
  (проверено: без фильтра — 415 значений, при Кабинет=CloudSix — 76, при
  Hauser — 70).

- **Папки** — используются для логического деления по разрезам аналитики.
  Например, все проверки, чек-листы ошибок и сверки (reconciliation)
  складываются в папку `Тесты / Чеки`, а не вперемешку с продуктовыми
  отчётами.

- **Один источник истины для формул.** Если метрика уже посчитана в
  какой-то Model — новая карточка/дашборд ссылается на эту Model через
  конструктор запросов (или `{{#<id модели>}}` в native SQL), а не
  копирует SQL-выражение заново. Формула правится один раз в Model — все
  карточки, построенные на ней, подхватывают правку автоматически. См.
  инцидент 2026-09-03 в чёрном списке антипаттернов ниже — до модели одна
  и та же формула была продублирована независимо в трёх местах и разошлась.

Это правило проверяется в `/review-task`, если задача создаёт/меняет
сущности в Metabase — по имени и расположению папки, а не только по
формулам/SQL.

## Семантический слой для AI-бота (решение 2026-09-05)

Платформа готовится к тому, что поверх Metabase/ClickHouse встанет AI-бот,
отвечающий на аналитические вопросы. Это меняет требования к тому, где
живут формулы и данные — не только человек должен их понимать, но и бот.

- **Формулы метрик — ClickHouse VIEW, а не только Metabase Model.**
  Metabase Model хранит SQL в своей app-БД — невидим для всего, что
  обращается к ClickHouse в обход Metabase (в первую очередь для бота,
  если он пишет ad-hoc SQL напрямую). Формула считается один раз в VIEW
  (например, `wb_metrics_by_cabinet_month` в `src/schema_wb_metrics_views.sql`),
  Metabase Model становится тонкой обёрткой (`SELECT ... FROM view`),
  добавляющей только русские подписи колонок для дашборда — Field Filter
  сюда не входит: Metabase запрещает переменные/Field Filter в Модели на
  native SQL (проверено на проде 2026-09-05). См.
  `src/metabase_queries/wb_metrics_model.sql`.
- **`COMMENT COLUMN` на VIEW обязателен** для бизнес-значимых полей —
  туда переносятся пояснения вида «почему не qty, а текстовое поле» или
  «эта колонка на 100% пустая в реальных выгрузках, считаем иначе». Это
  единственный способ, которым бот через `system.columns` увидит семантику
  без чтения репозитория.
- **Приоритет источника данных для бота**: сначала Metabase REST API
  (`POST /api/card/:id/query` по существующим Model/Metric — не гонять
  большие данные в ClickHouse заново под уже посчитанный вопрос), и только
  если вопрос не покрыт существующей моделью — ad-hoc SQL к ClickHouse
  через отдельного read-only пользователя (ещё не заведён на 2026-09-05 —
  сделать до того, как бот получит доступ к БД; ingest-скрипты остаются на
  текущем пользователе с правом записи).
- **Ratio-колонки VIEW — не суммируются по месяцам, и это надо явно
  сказать боту.** VIEW обычно даёт помесячный грейн (одна строка = месяц).
  Если бот (или человек) захочет «годовое значение» для колонки вроде
  среднего чека/доли %/показателя-на-клиента, инстинктивный `sum()` по
  12 строкам даст неверное число — правильная формула почти всегда
  `sum(числитель) / sum(знаменателя)`, а не сумма готовых отношений. Для
  каждой такой колонки `COMMENT COLUMN` обязан явно предупреждать об этом
  и указывать, где считается правильный годовой итог (если он вообще
  где-то материализован — см. исключение из правила Визуалов выше и
  `docs/formulas/<клиент>.tex`).
- **OpenMetadata сознательно не берём.** Он рассчитан на multi-source
  enterprise-каталоги (отдельный Postgres/MySQL + Elasticsearch, лишний
  сервис на поддержке) — у нас один ClickHouse и один Metabase, овчинка не
  стоит выделки при текущем масштабе команды. Пересмотреть, если появится
  второй источник данных или вырастет команда. Глоссарий терминов
  (Кабинет/Бренд/Проект) остаётся в `docs/architecture-map.md`.

## Definition of Done (общий для всех задач)

### Параметризация SQL-запросов к ClickHouse (2026-08-23)

Плохо (`reconcile_wb.py`, было) — f-string, уязвимо к инъекции:
```python
where = f"cabinet = '{cabinet}'"
sql = f"SELECT ... WHERE {where} AND report_number = {report_number}"
client.query(sql)
```

Хорошо (`check_wb.py`, существующий паттерн в проекте) — параметризованный запрос:
```python
sql = "SELECT ... WHERE cabinet = {cabinet:String} AND report_number = {report_number:UInt32}"
client.query(sql, parameters={"cabinet": cabinet, "report_number": report_number})
```

-- 200+ строк CTE с формулами продаж/логистики/лояльности,

### Фильтр дашборда на одну карточку-Визуал (2026-09-15)

Задача: на `Дашборд - WB Полный отчёт по артикулу` фильтры Кабинет/Артикул
должны управлять только одним Визуалом, а не всеми карточками дашборда.

1. Таблица (без фильтров, только unpivot) — служебная, на дашборд не идёт:
   ```sql
   SELECT month, cabinet, sku, '01 Кол-во продаж' AS metric, toFloat64(sales_qty) AS value
   FROM wb_metrics_by_sku_month
   UNION ALL SELECT month, cabinet, sku, '03 Продажи', toFloat64(sales_amount) FROM wb_metrics_by_sku_month
   -- ... остальные показатели
   ```
2. Визуал поверх неё — обычная MBQL-карточка (`source-card` → Таблица,
   `aggregation: sum(value)`, `breakout: [metric, month]`), `display: "pivot"`.
   Фильтр в самой карточке НЕ прописывается.
3. На дашборде — `dashcard.parameter_mappings`, таргет указывает прямо на
   поле карточки по имени, без переменных/template-tag:
   ```json
   {"parameter_id": "<id фильтра Кабинет>", "card_id": 95,
    "target": ["dimension", ["field", "cabinet", {"base-type": "type/Text"}]]}
   ```
   Тот же `parameter_id`, замапленный только на `dashcard_id` этого Визуала
   (не смапленный больше ни на одну карточку) — и фильтр действует только на
   него.

Гочтя при проверке: `POST /api/card/:id/query` с `parameters` — это ДРУГОЙ
путь резолвинга (требует, чтобы `id` параметра совпадал с `id` в
`card.parameters`/template-tag, иначе параметр молча отбрасывается). Реальный
путь, которым дашборд рендерит фильтры — `POST
/api/dashboard/:dash-id/dashcard/:dashcard-id/card/:card-id/query`, где
`parameters` резолвятся через `dashboard.parameters` +
`dashcard.parameter_mappings` и работают именно так, как выше. Проверять
фильтры дашборда нужно через этот путь, а не через прямой query карточки.

### Ratio-строка в сводной Таблице — как пометить (2026-09-19)

Задача: строка «Средний чек» в `Таблица - Реальт - Ежемесячные метрики`
(id 186) — столбец «За год» не должен быть суммой 12 месячных средних.

Плохо — если бы это была MBQL Визуал-пивот таблица, «За год» посчитался
бы автоматически как `sum(value)` по всем строкам этой метрики за год —
для среднего чека это сумма 12 разных средних, бессмысленное число. Само
по себе так и произошло бы, поэтому этот дашборд — не MBQL-пивот, а
native SQL Таблица (осознанное исключение, см. правило выше).

Хорошо (`realt_monthly_metrics.sql`) — «За год» для ratio-строки считается
отдельной формулой, не `sum` от отображаемых по месяцам значений:
```sql
-- «За год» здесь — НЕ sum(avg_check) по месяцам (это была бы сумма
-- средних, бессмысленная величина), а выручка за год / визиты за год.
SELECT 5, 'Средний чек',
    sumIf(toFloat64("Средний чек"), toMonth("Месяц")=1), -- ...по месяцам — это просто селектор одного числа, не агрегация
    ...
    sum(toFloat64("Выручка")) / nullIf(sum(toFloat64("Визиты")), 0)  -- «За год» — своя формула
FROM {{#98}}
```
Плюс `COMMENT COLUMN avg_check` в `schema_realt_metrics_views.sql`
проговаривает то же самое для бота, и раздел «"За год" для ratio-метрик»
в `docs/formulas/realt.tex` — для человека.
