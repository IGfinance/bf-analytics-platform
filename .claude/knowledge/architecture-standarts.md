# Архитектурные стандарты — bf-analytics-platform

Живой документ. Пополняется по ходу задач: автоматически через `/review-task`
(когда находится новый повторяющийся тип проблемы) и вручную.

Обязателен к прочтению перед написанием кода в этом репозитории, в том числе
AI-инструментами подрядчиков (Claude Code, Cursor).

## Жёсткие правила (нельзя нарушать)

- Никаких секретов в коде — только через `.env` (см. `.env.example`,
  `webapp/.env.example`)
- Конфигурируемость: то, что может измениться (URL, лимиты, ключи, пути,
  идентификаторы) — выносится в конфиг/переменные окружения, не хардкодится
  в теле функции
- Модульность: одна функция/скрипт — одна ответственность. Не смешивать
  получение данных, обработку и вывод в одном блоке без возможности
  переиспользовать части по отдельности
- Любой внешний вызов (API, БД, файловая система, сеть) обязан обрабатывать
  ошибки — без try/except или эквивалента код не принимается
- Логирование по глобальным правилам (`~/.claude/CLAUDE.md → Логирование`):
  уровни DEBUG/INFO/WARNING/ERROR/CRITICAL, без секретов и PII
- Новый функционал или починка бага → тест или явный ручной чек-лист проверки

## Соглашения по Metabase

Применяется к любым сущностям, создаваемым в Metabase (dashboards.finance-black.ru).

- **Именование:** `"Сущность - Название"`, где «Сущность» — один из пяти
  типов:
  - **Таблица** — SQL-запрос с выгрузкой в табличном виде (Metabase question
    с табличным результатом)
  - **Визуал** — визуализация таблицы: сводная (pivot), график и т.д.
    (Metabase question с типом визуализации, отличным от Table)
  - **Модель** — Metabase Model (`type: "model"`): зафиксированный SQL-запрос,
    на который ссылаются остальные карточки через конструктор вместо
    копирования SQL. Формулы метрик живут здесь один раз, а не в каждой
    карточке отдельно — см. «Один источник истины для формул» ниже
  - **Метрика** — Metabase Metric (`type: "metric"`): сохранённая агрегация
    поверх модели/таблицы (например, `sum("Продажи")`), переиспользуемая как
    готовый блок в конструкторе запросов
  - **Дашборд** — комбинация визуалов на одном экране

  Примеры: `Таблица - Метрики для отчета Wb`, `Визуал - Отчетность Wb`,
  `Модель - WB метрики по кабинету и месяцу`, `Метрика - WB Продажи`.

- **Папки** — используются для логического деления по разрезам аналитики.
  Например, все проверки, чек-листы ошибок и сверки (reconciliation)
  складываются в папку `Тесты / Чеки`, а не вперемешку с продуктовыми
  отчётами.

- **Один источник истины для формул.** Если метрика уже посчитана в
  какой-то Model — новая карточка/дашборд ссылается на эту Model через
  конструктор запросов (или `{{#<id модели>}}` в native SQL), а не
  копирует SQL-выражение заново. Формула правится один раз в Model — все
  карточки, построенные на ней, подхватывают правку автоматически. См.
  инцидент 2026-09-03 в чёрном списке антипаттернов ниже — до модели одна
  и та же формула была продублирована независимо в трёх местах и разошлась.

Это правило проверяется в `/review-task`, если задача создаёт/меняет
сущности в Metabase — по имени и расположению папки, а не только по
формулам/SQL.

## Семантический слой для AI-бота (решение 2026-09-05)

Платформа готовится к тому, что поверх Metabase/ClickHouse встанет AI-бот,
отвечающий на аналитические вопросы. Это меняет требования к тому, где
живут формулы и данные — не только человек должен их понимать, но и бот.

- **Формулы метрик — ClickHouse VIEW, а не только Metabase Model.**
  Metabase Model хранит SQL в своей app-БД — невидим для всего, что
  обращается к ClickHouse в обход Metabase (в первую очередь для бота,
  если он пишет ad-hoc SQL напрямую). Формула считается один раз в VIEW
  (например, `wb_metrics_by_cabinet_month` в `src/schema_wb_metrics_views.sql`),
  Metabase Model становится тонкой обёрткой (`SELECT ... FROM view`),
  добавляющей только русские подписи колонок для дашборда — Field Filter
  сюда не входит: Metabase запрещает переменные/Field Filter в Модели на
  native SQL (проверено на проде 2026-09-05). См.
  `src/metabase_queries/wb_metrics_model.sql`.
- **`COMMENT COLUMN` на VIEW обязателен** для бизнес-значимых полей —
  туда переносятся пояснения вида «почему не qty, а текстовое поле» или
  «эта колонка на 100% пустая в реальных выгрузках, считаем иначе». Это
  единственный способ, которым бот через `system.columns` увидит семантику
  без чтения репозитория.
- **Приоритет источника данных для бота**: сначала Metabase REST API
  (`POST /api/card/:id/query` по существующим Model/Metric — не гонять
  большие данные в ClickHouse заново под уже посчитанный вопрос), и только
  если вопрос не покрыт существующей моделью — ad-hoc SQL к ClickHouse
  через отдельного read-only пользователя (ещё не заведён на 2026-09-05 —
  сделать до того, как бот получит доступ к БД; ingest-скрипты остаются на
  текущем пользователе с правом записи).
- **OpenMetadata сознательно не берём.** Он рассчитан на multi-source
  enterprise-каталоги (отдельный Postgres/MySQL + Elasticsearch, лишний
  сервис на поддержке) — у нас один ClickHouse и один Metabase, овчинка не
  стоит выделки при текущем масштабе команды. Пересмотреть, если появится
  второй источник данных или вырастет команда. Глоссарий терминов
  (Кабинет/Бренд/Проект) остаётся в `docs/architecture-map.md`.

## Definition of Done (общий для всех задач)

- [ ] Нет захардкоженных секретов/токенов/путей, специфичных для окружения
- [ ] Все внешние вызовы (API, БД, файлы, сеть) обёрнуты в обработку ошибок —
      сбой одного вызова не роняет весь процесс/сервер
- [ ] Пользовательский ввод валидируется (тип, формат, размер файла и т.д.)
- [ ] Есть логи ключевых событий и ошибок (без секретов/PII)
- [ ] Код соответствует структуре, согласованной в разделе «Архитектура» ТЗ
- [ ] Задача проверена вручную по своему специфичному чек-листу из ТЗ

## Golden examples (до/после)

_Короткие сниппеты реального кода — что было и как исправлено. Учит
нагляднее, чем текстовые формулировки правил._

### Параметризация SQL-запросов к ClickHouse (2026-08-23)

Плохо (`reconcile_wb.py`, было) — f-string, уязвимо к инъекции:
```python
where = f"cabinet = '{cabinet}'"
sql = f"SELECT ... WHERE {where} AND report_number = {report_number}"
client.query(sql)
```

Хорошо (`check_wb.py`, существующий паттерн в проекте) — параметризованный запрос:
```python
sql = "SELECT ... WHERE cabinet = {cabinet:String} AND report_number = {report_number:UInt32}"
client.query(sql, parameters={"cabinet": cabinet, "report_number": report_number})
```

### Одна Model вместо копий SQL в Metabase (2026-09-03)

Плохо (было) — карточка `Таблица - Полный отчет Wb` пересчитывает формулы
метрик заново прямо в native SQL:
```sql
-- 200+ строк CTE с формулами продаж/логистики/лояльности,
-- независимая копия того же, что уже посчитано в reconciliation_rules_wb.yaml
WITH base AS (SELECT ... coalesce(sum(loyalty_discount_compensation), 0) AS sum_loyalty_comp ...)
```

Хорошо — карточка ссылается на Model через `{{#<id>}}`, формула живёт в одном месте:
```sql
SELECT "Месяц" AS month, '13 Скидка Wibes' AS metric, toFloat64("Скидка Wibes") AS value
FROM {{#49}}
```
