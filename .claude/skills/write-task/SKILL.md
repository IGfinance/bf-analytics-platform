# /write-task

Веду пользователя через 6 этапов интервью, чтобы собрать ТЗ, которое Илья
сможет выполнить с минимумом итераций. Перед началом прочитай
`.claude/knowledge/architecture-standarts.md` — он даёт контекст по жёстким
правилам проекта (если есть `.claude/architecture.md` — прочитай и его).
Если есть `docs/vision.md` — прочитай и его, чтобы понимать, в какую общую
картину вписывается новая задача. Если есть `docs/glossary.md` — прочитай и
его: термины проекта должны использоваться в ТЗ так же, как там определены.

Веди диалог по одному этапу за раз, не вываливай все вопросы сразу. После
каждого этапа кратко резюмируй, что зафиксировали, прежде чем идти дальше.
Используй AskUserQuestion там, где вопрос сводится к выбору из вариантов —
но не для открытых, содержательных вопросов (цель, архитектура и т.п.).

По ходу всего интервью следи за терминами. Если пользователь называет одну
и ту же сущность по-разному, или использует термин, для которого нет чёткого
определения — останови и уточни значение, затем добавь/поправь строку в
`docs/glossary.md` (создай файл с таблицей `Термин | Определение | Синонимы
| Где живёт`, если его ещё нет). Дальше в этом и всех следующих ТЗ используй
только термин из глоссария.

## Этап 1 — Задача

Собери формулировку в фиксированном формате: **«Нам нужно изменить {что},
чтобы {лучше заработало / появилось / перестало быть} {что}»**, плюс список
условий, которым должен соответствовать результат. Вопросы для сбора:

- Какую проблему решаем? Что не так сейчас конкретно (что именно менять)?
- Что должно получиться (заработать лучше / появиться / исчезнуть)?
- Что будет, если не делать?
- По каким конкретным условиям поймём, что результат готов и правильный?
  (список — станет `## Условия результата` в файле)

## Этап 2 — Пользователь и выгодоприобретатель

- Кто напрямую пользуется результатом?
- Кто выгодоприобретатель, если это другой человек/процесс?
- Как поймём, что стало лучше?

## Этап 3 — Архитектура (совместная проработка + каркас)

- Спроси, как пользователь видит решение (свободный текст)
- Сверься с `architecture-standarts.md` и текущим стеком проекта
- Если видишь более удачный вариант — предложи 1–3 альтернативы с плюсами и
  минусами, объясни, почему она лучше впишется в систему
- Зафиксируй финальное архитектурное решение и с чем оно должно быть
  совместимо (существующие модули/БД/API)
- **Сгенерируй минимальный каркас** (skeleton): структура файлов/папок,
  сигнатуры функций/классов, интерфейсы, комментарии-заглушки на местах, где
  должна быть логика. Не пиши реальную реализацию — только форму. Каркас
  ограничивает пространство для «плохой архитектуры» сильнее, чем текстовое
  правило. Спроси пользователя, закоммитить ли пустые файлы каркаса в
  репозиторий, чтобы Илья начинал с них, или оставить каркас только в ТЗ
- Составь список систем/компонентов, которых **вероятно** коснётся задача
  (например: ClickHouse, Metabase, webapp загрузки отчётов) — это идёт в
  человеческий файл как ориентир, явно помеченный необязательным (Илья может
  решить задачу иначе, если найдёт путь без изменения части из них)

## Этап 4 — Ограничения

- Технические: стек, что нельзя трогать, это временное решение или фундамент
  продукта
- Бизнес/срок
- Подтяни жёсткие правила из `architecture-standarts.md`, спроси — нужны ли
  специфичные для этой задачи ограничения
- Сформулируй отдельным заметным блоком **«Что НЕ делать»** — конкретные для
  этой задачи запрещённые практики (не общие фразы, а то, что реально может
  пойти не так именно здесь)

## Этап 5 — Надёжность и наблюдаемость

- Какие сценарии отказа критичны (упал внешний API, битый файл, нет сети,
  невалидный ввод)?
- Как узнаем, что что-то сломалось (логи/алерты/метрики)?
- Нужны ли тесты именно для этой задачи и какие

## Этап 6 — Исполнение и объём

- Кто делает, какой дедлайн
- **Оцени объём.** Если по совокупности этапов 3–5 выходит больше недели
  работы — предложи разбить на 2–3 под-ТЗ с собственным Definition of Done у
  каждой, чтобы контрольные точки появились сами по себе (конец подзадачи),
  без формальных митингов
- Формат сдачи (ветка/PR, что прислать)

## Имя файла

Формат: `{номер}-{кто}-{ГГММДД}-{блок}-{задача}.md`

- **номер** — сквозной номер задачи, 2 цифры (`01`, `02`, ...), общий для
  обоих файлов пары и для её review-отчёта. Определи следующий номер сам:
  просмотри `work/tz/active/`, `work/tz/done/` и `work/tz/review/`, найди
  максимальный номер среди уже существующих файлов, следующий — на 1 больше.
  Не веди отдельный счётчик в файле — номер всегда выводится из содержимого
  папок, чтобы не рассинхронизироваться.
- **кто** — `Чел` (человеческая часть) или `Тех` (техническая часть)
- **ГГММДД** — дата без разделителей, например `260816`
- **блок** — какой продукт/область проекта затрагивает задача. Спроси
  пользователя, к какому блоку относится задача (через AskUserQuestion) —
  список блоков для этого проекта ведётся здесь и пополняется с явного
  подтверждения пользователя при появлении нового блока
- **задача** — 2-4 слова ключевыми словами, латиницей/транслитом, через дефис
  (например `wb-sverka-otcheta`)

Пример пары файлов: `01-Чел-260816-platform-wb-sverka-otcheta.md` +
`01-Тех-260816-platform-wb-sverka-otcheta.md`.

Уточни блок у пользователя перед сборкой файлов, если из этапов 1-2 это не
очевидно.

## Финал — сборка файлов

ТЗ всегда состоит из **двух файлов** в `work/tz/active/`, чтобы Илья не тонул
в архитектуре, читая цель задачи. Первый файл — человеческий, короткий,
без кода/SQL/схем. Второй — технический, открывается по ходу реализации.

Создай `work/tz/active/{номер}-Чел-{ГГММДД}-{блок}-{задача}.md` (человеческая часть):

```markdown
# {Название задачи}

Техническая часть — см. [{номер}-Тех-{ГГММДД}-{блок}-{задача}.md]({номер}-Тех-{ГГММДД}-{блок}-{задача}.md).
Открывать по ходу реализации, не обязательно читать сразу целиком.
{если в тексте используются термины из глоссария — сослаться на него:
`[глоссарий проекта](../../../docs/glossary.md)`, путь относительно
`work/tz/active/`}

## Задача
Нам нужно изменить **{что меняем}**, чтобы {лучше заработало / появилось /
пропало} **{что}**.

## Условия результата
- [ ] {условие 1}
- [ ] {условие 2}
- [ ] ...

## Каких систем может коснуться (ориентир, не обязательство)
{список из этапа 3 — Илья может решить задачу и без изменения части из них,
если найдёт более удачный путь}
- {система А}
- {система Б}

## Пользователь / выгодоприобретатель
{этап 2}

## Исполнение
- Исполнитель: ...
- Дедлайн: ...
- Как сдавать: ...

## Changelog
- {ГГММДД}: создано
```

Создай `work/tz/active/{номер}-Тех-{ГГММДД}-{блок}-{задача}.md` (техническая часть):

```markdown
# {Название задачи} — техническая часть

Человеческая часть — см. [{номер}-Чел-{ГГММДД}-{блок}-{задача}.md]({номер}-Чел-{ГГММДД}-{блок}-{задача}.md).

## Архитектура
{согласованное решение, этап 3}

### Каркас
{сгенерированный skeleton или ссылка на закоммиченные файлы}

## Ограничения
{этап 4}

### Что НЕ делать
{явный список}

## Надёжность и проверки
{этап 5}

## Definition of Done (техническое)
{общий чек-лист из architecture-standarts.md + специфичные пункты этой задачи}

## Self-check перед сдачей
Илья заполняет и присылает вместе с результатом:
- [ ] ...
- [ ] ...
(зеркалит Definition of Done в форме чек-листа, который реально заполнят)

## Changelog
- {ГГММДД}: создано
```

Если задачу разбили на подзадачи (этап 6) — создай отдельную пару файлов на
каждую, с общим changelog-заголовком и ссылками друг на друга.

## Обнови видение

Если в проекте есть `docs/vision.md` — добавь новую строку в таблицу
«Прогресс» (какую часть видения закрывает эта задача, статус «не начато») со
ссылкой на новый файл. Если задача не относится ни к одной части видения —
пропусти этот шаг, не выдумывай связь искусственно.

В конце выведи в чат готовый текст сообщения для мессенджера (ссылка на
человеческий файл + резюме в 3–4 строки) — без лишних деталей, чтобы сразу
скопировать и отправить Илье.
