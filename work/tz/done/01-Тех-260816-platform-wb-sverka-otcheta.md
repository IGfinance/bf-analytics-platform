В `src/scripts/clickhouse/` уже реализован и задеплоен (report.finance-black.ru/cloudsix)
фундамент для сбора сырых данных:

| Компонент | Что делает |
|---|---|
| `webapp/app.py` (Flask) | Веб-форма: пачка `.xlsx` еженедельных детальных отчётов WB → привязка к кабинету (сейчас — свободный текст) |

### Решение по этому ТЗ

**1. Кабинет — выпадающий список с возможностью добавить новый**

На обеих формах загрузки (сырые данные и сводный отчёт) заменить свободный
текстовый ввод кабинета на `<input list="cabinets">` (datalist), заполняемый
через `SELECT DISTINCT cabinet FROM wb_reports` при рендере страницы. Поле
остаётся текстовым — можно вписать новое имя, если кабинета ещё нет в списке.
Отдельная таблица/конфиг под список кабинетов не нужна — источник истины
уже есть в `wb_reports`.

**2. Загрузка сводного отчёта**

Разобрана реальная структура файла (см. приложенный тестовый файл
`reports-test/WB/CloudSix - WB/Еженедельный отчет 2025-06-30 - 2026-08-09_250015250.xlsx`,
лист `Sheet1`, одна строка = один `report_number`):

`№ отчета`, `Юридическое лицо`, `Дата начала`, `Дата конца`, `Дата формирования`,
`Тип отчета` (Основной / По выкупам), `Продажа`, `В том числе Компенсация скидки
по программе лояльности`, `К перечислению за товар`, `Согласованная скидка, %`,
`Стоимость логистики`, `Стоимость хранения`, `Стоимость операций на приемке`,
`Прочие удержания/выплаты`, `Общая сумма штрафов`, `Корректировка Вознаграждения
Вайлдберриз (ВВ)`, `Стоимость участия в программе лояльности`, `Сумма баллов,
удержанных по программе лояльности`, `Разовое изменение срока перечисления
денежных средств`, `Итого к оплате`, `Валюта`.

Новая таблица `wb_report_summary` (по аналогии с `wb_reports`, дедуп через
`ReplacingMergeTree` по `(cabinet, report_number)`) хранит эти строки.
Загрузка — через новый роут в том же `webapp/app.py`, тот же выпадающий
список кабинетов (см. п.1), тот же паттерн, что и для сырых файлов
(временное сохранение → парсинг → запись → удаление временного файла).

**3. Сверка сырых данных со сводным отчётом**

Конфигурируемый маппинг `reconciliation_rules_wb.yaml` (по аналогии с
`column_mapping_wb.yaml`): колонка сводного отчёта → SQL-выражение
агрегации по `wb_reports` для того же `(cabinet, report_number)`.

**Точные формулы (какие сырые поля суммируются в какую колонку сводного
отчёта) в этом ТЗ не прописаны — их знает только Илья по опыту сборки
текущего Excel-отчёта. Это часть задачи: прописать/подтвердить формулы
в `reconciliation_rules_wb.yaml` перед тем, как сверка станет осмысленной.**
Не хардкодить формулы в Python — только в этом конфиге.

Допуск — точное совпадение (`tolerance: 0` по умолчанию, конфигурируется
на уровне отдельного правила, если для какой-то метрики точного совпадения
в принципе быть не может — например, из-за округлений WB).

Сверка запускается:
- автоматически сразу после загрузки сводного файла — по всем
  `report_number`, которые в нём есть;
- вручную через CLI (`reconcile_wb.py --cabinet X [--report-number N]`) —
  например, после дозагрузки пропущенных сырых данных.

Не блокирует загрузку — сырые данные и сводный отчёт сохраняются в любом
случае, расхождения только фиксируются как результат.

Результат сверки — статус на пару `(cabinet, report_number, метрика)`:
- `missing_raw` — report_number есть в сводном отчёте, но ни одной строки
  нет в сырых данных;
- `missing_summary` — report_number есть в сырых данных, но нет в сводном
  отчёте;
- `mismatch` — обе стороны есть, но конкретная метрика не сошлась (с точным
  значением расхождения);
- `ok` — сошлось.

Так по типу статуса сразу видно, «данные» это (файл не загружен/пропущен)
или «формула» (обе стороны есть, но не бьётся).

Результаты сверки — в новую таблицу `wb_reconciliation_results`, дальше
Илья строит по ней дашборд в Metabase (аналогично тому, как уже сделан
`wb_check_results` для проверок аномалий) — конкретные панели/визуализации
на усмотрение Ильи, минимум: сводка по статусам на кабинет за последний
запуск.

### Каркас

Каркас не коммитим в репозиторий — только текстом здесь, Илья создаёт файлы
сам по этой структуре:

- **`reconciliation_rules_wb.yaml`** — список правил: `summary_column`,
  `raw_expression` (SQL по `wb_reports`), `tolerance`, `notes`. Формулы —
  задача Ильи (см. выше).
- **`schema_wb_summary.sql`** — DDL для `wb_report_summary` (сводные данные,
  дедуп по `(cabinet, report_number)`) и `wb_reconciliation_results`
  (история сверок: `run_at`, `cabinet`, `report_number`, `status`,
  `summary_column`, `expected_value`, `actual_value`, `diff`).
- **`wb_summary_core.py`** — `parse_summary_file(path)`,
  `ingest_summary_files(paths, cabinet, log)` — по аналогии с `wb_core.py`.
- **`reconcile_wb.py`** — `load_rules()`, `reconcile_report(client, cabinet,
  report_number, rules)`, `run_reconciliation(client, cabinet,
  report_number=None)`, `main()` — по аналогии с `check_wb.py`.
- **`webapp/app.py`** — datalist кабинетов на обеих формах (заполняется
  `SELECT DISTINCT cabinet`) + новый роут загрузки сводного файла, вызывающий
  `ingest_summary_files()` и затем `run_reconciliation()`.

## Ограничения

- Стек фиксирован: Python 3.11 + ClickHouse + Flask/gunicorn, как в остальном
  `src/scripts/clickhouse/`. Никакой отдельной БД/фреймворка не добавлять.
- Существующие `wb_core.py`/`check_wb.py`/схему `wb_reports` можно менять,
  если это архитектурно оправдано (не запрещено правкой чего-то стороннего
  ради удобства) — но не ломать текущий поток загрузки сырых данных.
- Это фундамент, не одноразовое решение — дальше на нём строится сборка
  итогового отчёта и аналитика (см. карту модулей выше), поэтому маппинг и
  структура таблиц должны быть расширяемыми (аналогично `extra_columns` /
  `wb_unmapped_columns_log` в текущей схеме).
- Секреты (доступы ClickHouse, логин/пароль веб-формы) — только через
  `.env`, как сейчас. Ничего нового не хардкодить.

### Что НЕ делать

- **Не хардкодить формулы сверки в Python.** Только через
  `reconciliation_rules_wb.yaml` — иначе при любом уточнении формулы придётся
  лезть в код и пересобирать/деплоить, а не просто поправить конфиг.
- **Не сравнивать float на точное равенство (`==`).** Даже при
  `tolerance: 0` сравнение обязано идти через округление/эпсилон (например,
  `abs(diff) <= 0.01` рубля), иначе будут ложные `mismatch` из-за ошибок
  плавающей точки на ровном месте.
- **Не ронять загрузку сырых данных при добавлении сверки** — если в
  `webapp/app.py` что-то меняется в общей части (например, добавляется
  datalist), существующий маршрут загрузки сырых `.xlsx`-отчётов должен
  продолжать работать один в один, как сейчас.
- **Не терять/не игнорировать молча новые колонки** в файле сводного отчёта,
  которых нет в текущей структуре — фиксировать так же, как это уже сделано
  для `wb_unmapped_columns_log`, а не просто пропускать.

## Надёжность и проверки

Сценарии отказа, которые должны быть обработаны:
- Невалидный/битый `.xlsx` сводного отчёта или отсутствие ожидаемых колонок
  — понятная ошибка пользователю в форме, не падение всего процесса.
- Повторная загрузка того же сводного файла/`report_number` — дедуп через
  `ReplacingMergeTree`, не задвоение при подсчётах.
- Кабинет не выбран/пуст — валидация в форме (как уже сделано для сырых
  данных).
- Сбой записи в ClickHouse (`insert` упал) — обработка ошибки, понятный
  ответ пользователю, файл не считается загруженным молча «наполовину».

Логи — по паттерну уже существующих скриптов (структурированный вывод в
консоль/systemd journal при ручном запуске, плюс сам факт сверки и её
результат постоянно хранится в `wb_reconciliation_results` — это и есть
основной «лог» для этой задачи). Без секретов и PII.

Тесты: в проекте нет прецедента автотестов для python-скриптов
`scripts/clickhouse/` (у `wb_core.py`/`check_wb.py` их тоже нет) — по
аналогии закрываем **явным ручным чек-листом**, а не Playwright/pytest:
1. Прогнать сверку на приложенном тестовом файле
   (`reports-test/WB/CloudSix - WB/Еженедельный отчет 2025-06-30 -
   2026-08-09_250015250.xlsx`) после того, как соответствующие сырые данные
   по кабинету `CloudSix` загружены.
2. Убедиться, что для report_number, где сырые данные есть — статус `ok`
   или `mismatch` с конкретным числом расхождения (не падает с исключением).
3. Специально убрать один report_number из сырых данных (или взять сводный
   с report_number, которого точно нет в загруженных сырых) — статус должен
   быть `missing_raw`.
4. Проверить, что повторная загрузка того же сводного файла не создаёт
   задвоенных строк в `wb_report_summary`.
5. Проверить даталист кабинетов — новый кабинет, вписанный вручную,
   появляется в списке при следующей загрузке.

## Definition of Done (техническое)

- [ ] Нет захардкоженных секретов/токенов/путей, специфичных для окружения
- [ ] Все внешние вызовы (ClickHouse, файловая система) обёрнуты в обработку
      ошибок — сбой одного вызова не роняет весь процесс/сервер
- [ ] Пользовательский ввод валидируется (кабинет, формат файла)
- [ ] Есть логи ключевых событий и ошибок (без секретов/PII)
- [ ] Код соответствует структуре, согласованной в разделе «Архитектура»
- [ ] `reconciliation_rules_wb.yaml` заполнен реальными формулами (подтверждены
      Ильёй), а не заглушками
- [ ] Сравнение сумм идёт с допуском (эпсилон), не через `==`
- [ ] Существующая загрузка сырых данных по-прежнему работает без изменений
      в поведении
- [ ] Даталист кабинетов работает на обеих формах (сырые + сводный отчёт)
- [ ] В Metabase есть минимум одна панель/дашборд по `wb_reconciliation_results`
      со сводкой статусов по кабинету
- [ ] Задача проверена по ручному чек-листу из раздела «Надёжность и проверки»
