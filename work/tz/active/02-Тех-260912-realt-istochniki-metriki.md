# Реальт — источники данных и метрики в Metabase — техническая часть

Человеческая часть — см. [02-Чел-260912-realt-istochniki-metriki.md](02-Чел-260912-realt-istochniki-metriki.md).

## Архитектура

Прямое расширение уже устоявшегося паттерна проекта (новый источник = новый
модуль, `docs/vision.md`), без новых концепций сверх необходимого:

1. **`project_sources`** — новая таблица-реестр (project_id, source,
   added_at), аналог существующего `project_cabinets`/`platform`, но для
   источников без концепции «кабинета» (банк, карты, Клиентикс,
   Google-Таблицы). Решает жёсткое правило конфигурируемости: какие
   вкладки загрузки видит конкретный проект — это данные, не код. Какие
   источники умеет парсить код — отдельная константа `SUPPORTED_SOURCES`
   в `webapp/app.py` (по аналогии с уже существующим
   `SUPPORTED_PLATFORMS = {"wb"}`), её хардкодить нормально: добавление
   источника и так требует нового кода.

2. **Банк/карты — рефактор CLI в переиспользуемую функцию.** Сейчас
   `src/ingest_bank_statements.py`/`src/ingest_card_statements.py` — CLI
   с логикой в `main()` (`print`/`sys.exit`). Нужно вынести логику в
   `ingest_files(paths: list[Path], project_id: int, log=print) -> dict`
   (добавить в `bank_statement_1c.py`/`card_statement_pdf.py`), кидающую
   исключения вместо `sys.exit` — по образцу `wb_core.ingest_files`,
   который уже так вызывается из `webapp/app.py` (см.
   `upload_detail`/`upload_summary`). CLI-скрипты остаются тонкими
   обёртками поверх этой функции — не переписывать их логику, только
   извлечь в переиспользуемую форму.

3. **Новые источники Реальта** — Клиентикс и Google-Таблицы (зарплаты,
   расходы по статьям). Точный формат файлов неизвестен — уточняется по
   месту, когда появятся реальные образцы. Для Клиентикс закладывать
   построчную детализацию (пациент/врач/услуга/дата/сумма) — нужна для
   будущих LTV/юнит-экономики, даже если сами эти метрики не входят в
   объём этой задачи.

4. **Webapp** — отдельный роут на каждый источник (не общая форма с
   выбором типа) — так же, как сейчас разделены `/upload/detail` и
   `/upload/summary` для WB. Список видимых вкладок — из
   `project_sources` через новую `get_project_sources()` (аналог
   `get_project_platforms`, тот же паттерн try/except → `[]` при ошибке,
   чтобы отсутствие таблицы/сбой не ронял страницу загрузки).

5. **Семантический слой.** `realt_metrics_by_month` (ClickHouse VIEW) —
   формулы метрик считаются один раз здесь, `COMMENT COLUMN` на
   бизнес-значимых полях (см. «Семантический слой для AI-бота» в
   `architecture-standarts.md` и golden example
   `wb_metrics_by_cabinet_month`). Поверх — тонкая Metabase Model
   (`"Модель - Реальт метрики по месяцу"` или похожее имя, соглашение
   именования — см. `architecture-standarts.md`), в папке коллекции
   Реальта. Остальные карточки/дашборды ссылаются на неё через
   конструктор/`{{#id}}`, а не копируют SQL.

**Совместимость:** не меняет существующие WB/Ozon/CloudSix роуты, таблицы
и `project_cabinets`. Зависит от отдельной ClickHouse-базы для Реальта
(готовится отдельно, вне этой задачи) — см. «Ограничения».

## Ограничения

- Стек — тот же (Python, ClickHouse, Flask), новых зависимостей не
  закладываем; если под конкретный формат Клиентикс/Google-Таблиц
  понадобится библиотека — на усмотрение Ильи
- Это постоянное решение (Реальт — второй клиент платформы, не временный
  эксперимент)
- **Блокер:** не начинать до готовности отдельной ClickHouse-базы для
  Реальта — разграничение данных между проектами делается отдельно, не в
  рамках этой задачи. Пока БД не готова — Илья работает по каркасу и
  может уточнять формат Клиентикс/Google-Таблиц, но не пишет прод-код
  ingestion

### Что НЕ делать

- Не трогать существующие WB/Ozon-роуты, таблицы и схемы CloudSix —
  только additive-изменения
- Не привязывать источники Реальта к `project_cabinets`/«кабинет» — это
  не WB/Ozon-площадки, используем `project_sources`
- Не хардкодить slug/project_id/название «Реальт» в коде — только через
  данные (`projects`, `project_sources`), как для остальных проектов
- Не дублировать формулы метрик в отдельных Metabase-карточках — только
  через Model (антипаттерн 2026-09-03 в `architecture-standarts.md`:
  формулы разошлись, когда были скопированы в нескольких местах)
- Не собирать SQL через f-string с подстановкой пользовательского ввода —
  параметризованные запросы, `{param:Type}` + `parameters=` (антипаттерн
  2026-08-23 в `architecture-standarts.md`)
- Не использовать `print`/`sys.exit` в новых `ingest_files`-функциях,
  вызываемых из веба — только `log`-колбэк + исключения, иначе веб-форма
  упадёт без внятной ошибки

## Надёжность и проверки

Внешних API нет (все источники — ручная загрузка файлов), риски — «битый
файл» и «сорвалась запись в ClickHouse», не «упал внешний сервис»:

- Файл в неожиданном формате/со сдвинутой структурой колонок — не должен
  ронять веб-форму, пользователь видит понятную ошибку, а не голый 500
- Разрыв соединения с ClickHouse при записи — то же самое
- Повторная загрузка того же файла — не дублирует строки
  (`ReplacingMergeTree` + `source_file`/`row_num`, паттерн уже есть в
  `bank_statements`/`card_statements`)
- `project_id` берётся только из `g.project["id"]` (резолвится по slug +
  правам доступа через `project_access_required`), никогда из тела
  запроса от пользователя

**Особое замечание:** Клиентикс — данные клиники, вероятно содержат имена
пациентов. В логах (`logging`) не должно быть ФИО и другой
идентифицирующей информации — здесь цена ошибки выше, чем в логах
WB/Ozon.

Наблюдаемость — через существующий `logging`-паттерн webapp (INFO на
успешную загрузку с числом строк, ERROR на исключение), без секретов/PII.
Отдельные алерты/метрики не нужны — форма сразу показывает результат.

Тесты: форматы Клиентикс/Google-Таблиц пока неизвестны — полноценные
unit-тесты до появления реальных файлов не написать. Обязательно:
ручной чек-лист по каждому источнику (успешная загрузка + заведомо битый
файл не роняет форму) + юнит-тест на `parse_file`/`ingest_*`, когда
формат зафиксирован.

## Definition of Done (техническое)

Общее (из `architecture-standarts.md`):
- [ ] Нет захардкоженных секретов/токенов/путей, специфичных для окружения
- [ ] Все внешние вызовы (ClickHouse, файлы) обёрнуты в обработку ошибок —
      сбой одного вызова не роняет весь процесс/веб-форму
- [ ] Пользовательский ввод (файлы) валидируется (тип/размер/формат)
- [ ] Есть логи ключевых событий и ошибок, без секретов/PII (особое
      внимание — данные клиники)
- [ ] Код соответствует структуре, согласованной в разделе «Архитектура»

Специфичное для этой задачи:
- [ ] Банк/карты грузятся через веб-форму `report.`-поддомена (не только
      CLI, как сейчас)
- [ ] Клиентикс и обе Google-Таблицы (зарплаты, расходы) грузятся через
      веб-форму
- [ ] `project_sources` управляет видимостью вкладок — никакого хардкода
      `project_id`/slug Реальта в коде
- [ ] Существует ClickHouse VIEW с метриками (минимум — выручка по
      услугам), с `COMMENT COLUMN` на значимых полях
- [ ] Существует Metabase Model поверх VIEW, в правильной папке
      коллекции Реальта, по соглашению именования
- [ ] Формулы метрик вручную сверены с черновиком дашбордов Ильи —
      результат сверки описан в self-check
- [ ] Существующие WB/Ozon/CloudSix-функции не сломаны (ручной smoke-test)
