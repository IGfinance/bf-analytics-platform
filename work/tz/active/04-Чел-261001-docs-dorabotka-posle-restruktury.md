> Done пока нет — только сырые комментарии по итогам вычитки PR #6
> (`Docs-Remastered`).

## Конфиденциальность

- Не упоминать в документации, которая уходит на GitHub, названия клиентов.
  Если есть документы с названиями и информацией по клиентам (например,
  формулы метрик конкретного клиента) — такие файлы должны быть в
  `.gitignore`, а не в публичном репозитории.

## Разделить `vision.md` на три документа

- **Vision** — остаётся только концептуальное описание платформы: какие
  задачи она решает и как функционирует.
- **Бэклог** — отдельный файл. Возможно, стоит перенести его в саму папку
  проекта в вики (сейчас — Obsidian), чтобы Илья тоже мог его видеть —
  так, наверное, будет удобнее.
- **Ченджлог** — отдельный файл.

## Архитектурная карта (`architecture-map.md`)

- В каждый блок CLI / Веб-форма / Внешний API — подвести отдельными
  стрелочками сверху источники, которые уже подключены и работают:
  ПланФакт, WB, Ozon, 1С, Google-Таблицы и т.д.
- CLI-скрипты раскрыть отдельным списком ниже по документу: что есть, как
  работает.
- Баги в архитектуре не описывать — нужна именно фактура, как это работает
  сейчас. По API в идеале указывать коротким форматом, что именно тянем и
  как: например, что Ozon тянется разными API и потом цифры собираются
  особым способом, а не одной сплошной таблицей, как в xlsx.
- Историю изменений файлов Реальта в архитектуре не указывать — выглядит
  странно в этом документе.
- Логи изменений VIEW не нужны. Нужна чёткая фактура «как сейчас», без
  истории правок.
- Схему с тремя методами Ozon переделать — сейчас описана сумбурно, без
  логики. Формат: слева — методы и краткое описание, о чём метод;
  посередине — поля на выгрузку; справа — таблицы, куда ложатся данные.
- Metabase описывать отдельно двумя кусками: (1) схема по дашбордам и
  папкам, с коротким описанием, о чём дашборд; (2) отдельно — модели и
  метрики, если нужно.
- Количество строк в базе по проектам не указывать — при загрузке данных
  каждый час документацию придётся переписывать бесконечно. Вместо этого —
  отдельная документация, где фиксируется, какие типовые блоки подключены
  у какого проекта (WB, Ozon, ПланФакт и т.д.), без детализации по
  количеству строк в таблицах.
- Про AI-бота писать в vision, а не в архитектуре.

## Документ «1С OData» (сейчас `odata-alabuga-bottling.md`)

- Убрать из документа название компании (Алабуга Боттлинг). Это общий
  технический документ про работу с OData и выгрузками из 1С, а не про
  конкретного клиента. Пока что речь только про 1С Бухгалтерию.
- Убрать количество записей — это универсальный документ, который
  описывает, как бухгалтерские и другие данные из 1С будут обрабатываться
  и импортироваться в нашу базу, а не фиксирует текущий снимок цифр.
- Документ сейчас рабочий — нужен, чтобы наладить 1С: понять, какие
  таблицы есть при выгрузке и какие из них будем использовать. Пока не
  трогаем его в этом смысле. По итогам настройки 1С нужно будет отдельно
  сформировать финальный документ с полным техническим описанием работы с
  1С (уже не разведка, а то, как это устроено и работает).

## Документ формул Реальта (`realt.tex`)

- Не нравится, как сейчас выглядит: разные шрифты для англ/рус текста,
  вперемешку технические обозначения полей и человеческое описание. Нужно
  чётко разделить документ на две части:
  - **Человеческая логика расчётов** — без большого количества текста,
    лаконично и понятно, с формулами в человеческом виде.
  - **Техническая часть** — схемы, реальные названия столбцов, таблиц и
    т.д.
- Формулы нужны будут не только по Реальту, а универсальные + по
  проектам. Есть универсальные блоки (одинаковые для всех проектов):
  подключение ПланФакта, WB, Ozon, Транзакции. И есть индивидуальные вещи
  по конкретному проекту — например, расчёт зарплаты у Реальта,
  самовыкупы у CloudSix и подобное. Документ формул должен эту структуру
  отражать, а не быть одним файлом на клиента.

- У нас до сих пор очень слабое понимание, что такое VIEW, модель и
  метрика в нашей схеме — как это всё работает, какие слои VIEW есть, как
  они связаны друг с другом и как функционируют вместе. Это ключевая
  доработка, важнее остальных пунктов в этом файле.
