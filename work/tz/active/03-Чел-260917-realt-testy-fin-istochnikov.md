# Реальт — тесты для источников «Расчетный счет»/«Наличные»/«Начисления»

Техническая часть — см. [03-Тех-260917-realt-testy-fin-istochnikov.md](03-Тех-260917-realt-testy-fin-istochnikov.md).
Термины (Проект, Кабинет и т.д.) — см. [глоссарий проекта](../../../docs/glossary.md).

## Задача

Ты добавил 3 новых источника Реальта — «Расчетный счет», «Наличные»,
«Начисления» (тянутся из Google-Таблицы через API, по тому же принципу,
что и «Импорт ФОТ»/«Остальные расходы»). Код уже смерджен в master
(парсинг проверен вручную — синтетические данные, `py_compile`), но в
отличие от Клиентикс/ФОТ/Расходов, у которых есть `tests/test_realt_payroll.py`
и `tests/test_realt_expenses.py`, у новых трёх источников тестов нет.

Нужно закрыть этот пробел — чтобы будущая правка позиций колонок или
формата чисел/дат не сломала загрузку финансовых данных незаметно.

## Условия результата

- [ ] Юнит-тесты на `parse_bank_account`, `parse_cash`, `parse_accruals`
      (`src/realt_gsheets_core.py`) — по образцу существующих
      `tests/test_realt_expenses.py`/`tests/test_realt_payroll.py`
      (синтетический `values: list[list[str]]`, без обращения к Google
      Sheets API и ClickHouse)
- [ ] Тесты покрывают для каждого источника:
      - обычную строку с данными — все поля распознаются верно
      - декоративную/пустую строку без суммы — пропускается (`skipped`
        увеличивается, строка не попадает в результат)
      - числа в разных форматах источника (пробел-разделитель,
        неразрывный пробел, отрицательные, `-` как пусто)
      - даты: `ДД/ММ/ГГ` (`operation_date`/`accrual_date` в «Расчетном
        счете»/«Наличных») и `<день> <сокр.месяца>[.] <yy>` для
        `accrual_date` в «Начислениях» (включая нерегулярные сокращения
        месяцев, как уже есть в тесте на `_ru_month`)
- [ ] `pytest tests/` зелёный, без регрессий по остальным файлам

## Каких систем может коснуться

- `tests/test_realt_bank_account.py`, `tests/test_realt_cash.py`,
  `tests/test_realt_accruals.py` (новые файлы; можно объединить в один
  файл на все три источника, если так удобнее — жёсткого требования на
  разбивку нет)

## Пользователь / выгодоприобретатель

Ваша команда — чтобы будущие правки парсера (например, при изменении
формата вкладки клиентом) не тихо ломали загрузку финансовых данных
Реальта, а падали на тестах до продакшена.
